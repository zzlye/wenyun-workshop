# 账号登录与余额刷新失败排查

## 结论

北京时间 2026 年 10 月 21 日上午，部分网页版客户登录、刷新余额失败。已确认主要故障是内部第二跳代理覆盖了客户端来源地址，多个客户共用同一个 IP 限流桶，而不是已经证实的网站撞库导致服务不可用。

另有独立的 SSH 猜密码流量，不能与网站故障混为一谈。原始证据只在本地排查目录保存，本记录不包含客户账号、密码、令牌或完整访问日志。

## 证据

- 今天零点至约 10:56 的 NewAPI 日志中，内网代理地址触发了 1,670 次续期接口 429、49 次登录接口 429、46 次余额查询接口 429。
- 西米露入口日志显示，同期不同公网来源均受到影响；NewAPI 却把这些来源记录成同一个西米露容器地址。
- 运行中的 Caddy 在内部 3000 端口没有配置可信代理。它再次构建 `X-Forwarded-For`，丢失了外层 Caddy 已校验、Nginx 已转发的来源链。
- NewAPI 关键接口限制默认为每 IP 20 分钟 20 次。Redis 中实际共享桶计数已达 83，仍有 841 秒过期时间，因此等待 5 分钟或切换客户网络不能解决共享桶问题。
- 同一台排查电脑读取同一只读接口：经西米露返回 429，直接访问 API 返回正常业务权限拒绝 403。403 不是登录失败复现，而是证明请求已经通过限流层、进入原有权限检查。
- SSH 日志中今天零点至约 10:56 有 3,250 条密码失败记录；这个窗口内成功 SSH 登录均可对应本次排查连接。该结论不等于完整主机入侵排除。
- 补充按来源去重：上述 3,250 次密码失败来自 37 个不同 IP。截至 11:13:59 累计 3,281 次，仍为 37 个来源。不同 IP 不等于不同攻击者，不能由此认定是同一组织或针对本站的攻击。
- 网站同时存在配置文件路径扫描、定时重复登录请求。HTTP 200 不代表登录成功，且失败登录没有完整账号审计，不能仅凭次数认定撞库成功。

## 修复

经用户确认，只热加载 Caddy：在内部 3000 端口的 `reverse_proxy` 中，精确信任当前西米露容器 `172.19.0.4/32`，保留外层已校验的来源链。

- 公网 HTTPS 和公网直连 3000 请求仍不信任客户端自行填入的来源头。
- 不关闭限流，不清空限流数据库，不修改账号、支付或余额。
- 不重启 NewAPI、西米露、数据库或 Caddy，不重新发布 Docker、桌面客户端。
- 部署配置中的业务监听地址保持现场原值；本次只修改内部来源信任关系，不覆盖现有域名与上游端口。

服务器备份：`/opt/new-api/caddy/backups/account-ip-20261021T030617Z/`。

## 验证

1. 回归用例在修改前失败，修改后与已有 Nginx 账号代理用例共 4 项通过。
2. 线上 Caddy 候选配置验证通过，热加载成功，各服务启动时间未改变。
3. 同一排查请求经过网页和直接访问 API，NewAPI 均记录为同一个真实公网来源；不再记录为容器地址。
4. 分别向网页和公网 3000 端口传入伪造 `X-Forwarded-For`，NewAPI 仍记录实际来源，没有接受伪造地址。
5. 11:06:20 至 11:10:32 的网页版登录、续期、余额读取观察中没有 429，并出现正常续期与余额返回。业务审计也记录到修复后 4 个账号真实登录成功。
6. 用户指定的个别账号尚未出现新的成功登录事件，因此仍需由该客户刷新重试，不能把其他账号恢复当作该账号已验证。

## 保留事项

- 容器重建后如 IP 变化，必须核对 `docker inspect` 并同步更新这个单地址白名单；不能直接信任整个公网。
- 有些客户端已丢失或过期的刷新会话仍返回 401，需要重新登录；本次代理修复不伪造或绕过会话认证。
- SSH 密钥登录与密码策略仍需单独实施，先验证密钥登录和应急入口，再收紧密码登录。本次没有修改 SSH 认证方式；后续经用户确认实施的来源封禁见下节。
- 原始证据及复验脚本：`D:\tmp\audit-20261021`。

## 经用户确认封禁 SSH 来源

用户要求封禁上述全部来源后，于北京时间 11:18:32 加载 37 个地址的独立封禁表，仅禁止这些地址访问 TCP 22，不影响网站、API、其他端口或 Docker 转发。

- 固定名单为今天零点至 11:13:59 的失败来源，没有自动扩展到后来新出现的地址。
- 核对当前管理连接、留存日志中的成功 SSH 登录来源，均未与名单重合；名单只包含公网 IPv4 单地址，没有扩大成网段。
- 使用独立 `inet ximilu_ssh_blocklist` 表，未启用原本关闭的 UFW，未清空或替换现有 Docker/iptables 规则。
- 配置文件为 `/etc/nftables.d/ximilu-ssh-blocklist.nft`；由已启用的 `ximilu-ssh-blocklist.service` 在开机时恢复，不依赖临时命令存活。
- 配置加载前通过 `nft --check`，同时保留三分钟应急回退。11:19:40 全新 SSH 连接、完整 37 地址名单、服务启用状态、原有 iptables 规则及网站/API HTTP 200 均验证通过，随后取消应急回退。
- 验收时丢弃计数已为 20 个数据包，说明封禁规则实际命中；数据包数不是登录尝试次数。
- NewAPI、西米露、Caddy 启动时间均未变化，未重启业务。

本次备份与名单：`/opt/security/ssh-ban-20261021T031829Z/`。

如需撤销，仅以管理员身份执行该目录的 `ROLLBACK.sh`。脚本只禁用本次持久服务、删除本次独立表，不覆盖其他防火墙规则。这份固定名单不会自动扩展，后续自动封禁由下一节的 Fail2ban 独立负责。

## 安装 SSH 自动封禁

用户明确要求安装后，从 Ubuntu 软件源安装 Fail2ban 1.0.2，于北京时间 11:26 启用，仅监控 SSH 的 systemd 日志。

### 生效规则

- 每个来源 10 分钟内累计 5 次被 SSH 规则识别的失败事件，首次封禁 1 小时。
- 重复违规使用递增封禁，逐次加倍，上限 24 小时；到期自动解封。
- 只拦截 TCP 22，不根据网站 429 封禁，不影响 NewAPI 和西米露的 HTTP 服务。
- 管理白名单仅包括本机回环及已核实的当前管理出口单 IP，没有放行整个网段。管理出口改变时应重新核对白名单。
- 封禁历史保存七天，服务已设置开机启用，服务重启会恢复未到期封禁。
- 之前 37 个 IP 的固定封禁继续保留，不因自动封禁到期而解封。

### 验收

- `fail2ban-client --test` 通过，实际只启动 `sshd` 一个监控项。
- 只读抽样的 500 行真实 SSH 日志中，196 行被失败规则匹配，日期解析成功；成功登录及关联上下文不会简单按密码失败重复计数。
- 启动后从真实日志中自动封禁了两个已存在于固定名单的来源。这两项不是新增攻击者，也不是手工调用封禁命令制造的结果。
- 使用内置 `attempt` 接口和文档保留地址做受控验收：前四个模拟失败不封禁，第五个触发 3,600 秒封禁；内核规则中存在对应地址且只匹配 TCP 22；测试地址随后全部解封。没有向 SSH 提交错误密码，也没有修改系统认证日志。
- 单独重启 Fail2ban 后，两个真实封禁恢复成功，截止时间保持不变。该测试没有重启 SSH、数据库、Docker 或业务容器。
- 验收脚本曾因客户端输出格式解析失败而退出，修正解析后完整通过；失败发生在报告生成阶段，模拟封禁都已清理，不是防护服务故障。
- 新 SSH 连接、网站和 API HTTP 200 已验证；原有 iptables/Docker 规则未改变。

### 维护入口

- 当前状态：`fail2ban-client status sshd`
- 查看自动封禁及期限：`fail2ban-client get sshd banip --with-time`
- 解除某个自动封禁：`fail2ban-client set sshd unbanip <IP>`。若该 IP 也在固定 37 个名单中，还需单独解除固定名单规则。
- 配置：`/etc/fail2ban/jail.d/99-ximilu-sshd.local`、`/etc/fail2ban/fail2ban.local`。
- 脱敏配置示例：`deploy/security/sshd.local.example`、`deploy/security/fail2ban.local.example`。部署时需填入核实过的管理白名单，不能直接假定来源地址。
- 备份、验收与回退：`/opt/security/fail2ban-20261021T032438Z/`。其中 `ROLLBACK.sh` 只停用自动防护，不解除固定 37 个封禁。
- 本地验收记录：`D:\tmp\audit-20261021\fail2ban-behavior.txt`。

自动封禁无法完全阻止低频、分散 IP 尝试。SSH 密钥登录及关闭密码登录尚未实施，需在验证备用管理入口后另行安排。
